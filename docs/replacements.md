# Заказы серверов и автозамена UpCloud и Virtua.Cloud

Раздел **Автозамена** заменяет привязанный сервер, когда DNS Guard пять минут подряд подтверждает блокировку его публичного IPv4. Отсчёт начинается после достижения порога ошибок пула и исключения A-записи. Защищённая последняя A-запись тоже подходит. Для каждого узла требуется явное разрешение на удаление сервера. После обновления приложения все существующие узлы начинают с выключенной автозаменой.

## Ansible для заказов серверов

Образ backend содержит плейбуки для обычных нод (`nodes`) и нод за CDN (`nodes_wl`), их роли, файлы развёртывания и коллекции. При сборке они загружаются из зафиксированной ревизии основной ветки `mitetenov/ansible`. Для заказов DNS Guard формирует inventory с одной нодой, подставляет её домен и ключ Remnawave. Приватный SSH-ключ и настройки групп подключаются с машины развёртывания. Встроенный комплект пропускает установку Alloy, поскольку исходный шаблон настроен для конкретной установки Grafana. [Ревизия Ansible в образе](https://github.com/mitetenov/ansible/tree/d08132cf664ed60174292e09565342dda0e267fb)

1. Укажите в `.env` `REPLACEMENT_ANSIBLE_SSH_KEY_BASE64` со всем содержимым приватного SSH-ключа в Base64 одной строкой. Ключ должен работать без запроса пароля. Храните `.env` с правами `0600`. По умолчанию для входа используется `root`. Для другого пользователя задайте `REPLACEMENT_ANSIBLE_SSH_USER` в `.env` и настройте повышение привилегий на нодах.

   Для подключения ключа файлом задайте `REPLACEMENT_HOST_DIR=./replacement` и положите ключ в `replacement/ssh_key` рядом с `docker-compose.yaml`. Можно указать абсолютный путь к каталогу на хосте. Внутри backend каталог доступен только для чтения по пути `/run/dns-guard/replacement`. Backend работает под UID 10001, которому нужны проход по каталогам и доступ на чтение ключа с правами `0600` или `0400`. Если заданы оба источника, ключ из `REPLACEMENT_ANSIBLE_SSH_KEY_BASE64` имеет приоритет.

2. Укажите свой email для Certbot в `REPLACEMENT_ANSIBLE_CERTBOT_EMAIL` в `.env`. Для типа `nodes_wl` добавьте `REPLACEMENT_ANSIBLE_XHTTP_PATH` из профиля Remnawave. Путь начинается и заканчивается косой чертой. Если профиль использует порт, отличный от 8443, задайте `REPLACEMENT_ANSIBLE_XHTTP_UPSTREAM=127.0.0.1:<порт>`. У обычной ноды стандартный TLS-вход nginx слушает `127.0.0.1:4321` с PROXY protocol.

   Каталог `replacement/group_vars` можно использовать для переопределений в `all.yml`, `nodes.yml` и `nodes_wl.yml`. Значения из этих файлов имеют приоритет над стандартными параметрами и настройками Certbot и XHTTP из `.env`. Произвольный путь внутри контейнера задаётся через `REPLACEMENT_ANSIBLE_GROUP_VARS_DIR`.

3. Запустите Compose из каталога установки. Для перехода с двух Compose-файлов сначала обновите основной `docker-compose.yaml` и удалите `COMPOSE_FILE` из `.env`. [Основной файл Compose](../docker-compose.yaml)

   ```sh
   docker compose config --quiet
   docker compose up -d
   ```

При обновлении со стандартной установки с внешним репозиторием backend также подхватывает `replacement/ansible/inventory/group_vars`, если `replacement/group_vars` отсутствует. Чтобы использовать плейбуки из образа, удалите `REPLACEMENT_ANSIBLE_REPO_DIR` из `.env`. Если внешний репозиторий нужен для ручных привязок, задайте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR=/run/dns-guard/replacement/ansible`. Чтобы использовать внешние плейбуки для обоих режимов, оставьте `REPLACEMENT_ANSIBLE_REPO_DIR` с путём к смонтированному репозиторию.

### Плагин ноды Remnawave

Выберите существующий плагин Remnawave на экране подтверждения заказа или в привязке автозамены. При заказе плагин назначается при регистрации новой ноды. При автозамене плагин из привязки назначается при обновлении ноды, до проверки нового IP. Вариант «Сохранить текущий плагин» оставляет активный плагин ноды в Remnawave.

Токену Remnawave нужны права на чтение списка плагинов и на создание или изменение нод. Встроенный плейбук разворачивает контейнер с `NET_ADMIN`. При использовании своего плейбука добавьте это разрешение в Compose-файл ноды и проверьте требования к версии Remnawave, ядру и `nftables`. [Требования к плагинам нод](https://docs.rw/learn/node-plugins/#требования)

## Автозамена UpCloud с ручной привязкой

Для ранее установленных нод нужен внешний inventory с параметрами конкретных хостов. Заказанные через DNS Guard ноды получают автозамену на основе настроек групп и сохранённого публичного ключа хоста.

1. На машине развёртывания подготовьте рабочую копию рядом с `docker-compose.yaml`. Установите коллекции в каталог этой копии с помощью `ansible-galaxy` из Ansible Core. В `.env` задайте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR=/run/dns-guard/replacement/ansible`.

   ```sh
   mkdir -p replacement/node_vars
   git clone https://github.com/mitetenov/ansible.git replacement/ansible
   git -C replacement/ansible checkout --detach d08132cf664ed60174292e09565342dda0e267fb
   (cd replacement/ansible && ansible-galaxy collection install -r requirements.yml -p ./collections)
   ```

2. Для каждой ранее установленной ноды, которую вы подключаете вручную, создайте `replacement/node_vars/<uuid-ноды-remnawave>.json`. Укажите UUID в нижнем регистре. В качестве `inventory_hostname` используйте имя узла из `inventory/hosts.yml`. Например, файл для ноды, зарегистрированной как `finland-01`, выглядит так.

   ```json
   {"inventory_hostname": "finland-01"}
   ```

   | Группа в inventory | Плейбук |
   | --- | --- |
   | `nodes` | `playbooks/nodes.yml` |
   | `nodes_wl` | `playbooks/nodes-wl.yml` |

   Домен и параметры узла берутся из переменных хоста и группы. Новый IPv4 подставляется на время запуска. Для последующих ручных запусков этого inventory используйте актуальный адрес узла. Роль `stack_nodes` сохраняет существующий `/opt/remnawave-node/.env` на перенесённом диске. Если его предстоит создать, задайте `stack_node_secret_key` или `stack_nodes_env_content` в настройках ноды.

3. Для ранее установленной ноды создайте `replacement/known_hosts` с проверенным публичным **ключом хоста** исходной VM. Вместо имени сервера укажите UUID ноды Remnawave. Эта привязка позволяет проверить тот же ключ на новом IP при переключении SSH между портами 22222 и 22.

   ```text
   <uuid-ноды-remnawave> ssh-ed25519 <публичный-ключ-хоста-в-base64>
   ```

4. Задайте пути в `.env` и запустите `docker compose up -d`.

   ```dotenv
   REPLACEMENT_HOST_DIR=./replacement
   REPLACEMENT_ANSIBLE_SSH_KEY=/run/dns-guard/replacement/ssh_key
   REPLACEMENT_ANSIBLE_NODE_VARS_DIR=/run/dns-guard/replacement/node_vars
   REPLACEMENT_ANSIBLE_KNOWN_HOSTS=/run/dns-guard/replacement/known_hosts
   ```

   В **Настройках** подключите Cloudflare и Remnawave. Для Cloudflare нужны чтение зоны и изменение DNS. Для Remnawave нужны чтение нод и хостов, изменение адреса ноды и хостов с явным IP. В **Настройках → Интеграции → Хостинги и Ansible** сохраните API-токен UpCloud с доступом к VM, дискам, планам, интерфейсам, правилам firewall и управлению публичными IP. Для целевого узла укажите UUID VM и ноды, разрешите замену и включите автоматизацию пула.

Если на узле включён Certbot, плейбук использует сертификаты с перенесённого диска. Для выдачи или продления через HTTP-01 домен `nginx_node_domain` должен вести к доступному ACME webroot в момент запуска роли `ssl`. Это важно для индивидуального домена ноды или отдельного CDN origin. Смена A-записи пула происходит после Ansible и успешных проверок.

## Заказ нового сервера

В боковом меню откройте **Серверы**. В настройках нужного DNS-пула задайте шаблон индивидуального домена ноды. У пула должны быть профиль проверок DNS Guard и соответствующий хост в Remnawave. Шаблон должен порождать домен в той же зоне Cloudflare. Переменная `{n}` обязательна и даёт порядковый номер, `{country}` подставляет код страны хостинга в нижнем регистре, `{pool}` подставляет полное имя пула. Например, `{country}-{n}.{pool}` для пула `eu.example.com` и Германии даёт `de-01.eu.example.com`. Шаблон можно изменить для следующих заказов. Пустое значение убирает пул из списка для новых заказов.

1. В строке UpCloud нажмите **Заказать сервер** и выберите страну с конкретной зоной. DNS Guard читает публичные локации из UpCloud и загружает тарифы для выбранной зоны. Для каждого тарифа показываются CPU, память, диск и почасовая цена в валюте аккаунта. Поддерживаются постоянные VM с включённым диском и публичным IPv4. Доступность ресурсов UpCloud подтверждает при создании.
2. Выберите DNS-пул, тип ноды (`nodes` или `nodes_wl`) и существующий профиль Remnawave. Нода получает входящие подключения выбранного профиля. Профиль должен иметь хотя бы одно подключение, назначенное хосту этого пула в панели.
3. Проверьте выбор и подтвердите платный заказ. Мастер заранее проверяет SSH-ключ, формат HTTPS-адреса панели и настройки плейбука для выбранного типа ноды. DNS Guard повторно проверит цену и конфигурацию тарифа до отправки запроса. В истории заказа можно следить за этапами и отменить заказ до отправки запроса на создание VM.
4. DNS Guard создаёт VM из публичного образа Debian 13, получает её публичный SSH-ключ через HTTPS и создаёт индивидуальную A-запись для домена ноды. Затем регистрирует ноду в Remnawave и запускает плейбук с выбранными группой и доменом. Публичный адрес пула получает новый IP после успешных проверок. В подходящих хостах Remnawave сохраняются существующие назначения.
5. После завершения DNS Guard включает автозамену для созданного сервера. Для работы замены должна быть включена автоматизация самого пула. При пересоздании VM индивидуальное имя сохраняется, а его A-запись переводится на новый IP до запуска Ansible.

На внешнем HTTPS-адресе `PUBLIC_ORIGIN` для новой VM должен быть доступен `POST /api/server-orders/<uuid>/enroll`. Маршрут принимает одноразовую регистрацию с токеном конкретного заказа. Если внешний прокси требует дополнительный вход, откройте только этот маршрут для регистрации. Запрос POST без токена к этому маршруту должен вернуть ответ DNS Guard `401 Invalid enrollment credential`. Доступ к остальным операциям управления по-прежнему требует сессию администратора.

Если backend требует каталог `group_vars` при стандартной установке, обновите образ и проверьте, задан ли явный путь `REPLACEMENT_ANSIBLE_GROUP_VARS_DIR` в `.env`. После изменения настроек запустите `docker compose up -d --no-deps backend`. Заказ на этапе «Проверка заказа» продолжится автоматически после исправления.

Для новых серверов UpCloud и Virtua.Cloud отсчёт 10 минут начинается после настройки и добавления цели для проверок. Если к этому моменту успешных проверок не было, а свежие результаты работающих чекеров подтверждают недоступность по правилам пула, DNS Guard удаляет VPS и его настройки и один раз повторяет платный заказ в той же локации по тому же тарифу. Имя домена и резерв автохоста сохраняются. Повторный VPS получает свои 10 минут на проверку. Если он тоже недоступен, DNS Guard удаляет его, освобождает слот автохоста и завершает заказ с ошибкой. За ходом операции можно следить в логах заказа. Для очистки токенам нужны права удаления VPS, ноды Remnawave и DNS-записей заказа.

Для заказа токену UpCloud также нужен доступ к спискам зон, тарифов, цен и публичных образов, к валюте аккаунта и созданию облачных серверов и дисков с метками. Токен Remnawave должен позволять читать профили и ключ установки ноды, создавать ноды и обновлять назначения хостов. Индивидуальная A-запись создаётся без проксирования и помечается идентификатором заказа. При конфликте домена проверьте историю до повторного заказа. Если ответ при создании VM потерян, DNS Guard продолжает искать тот же сервер. Доступное в истории повторное создание требует проверки отсутствия сервера в UpCloud.

### Скрытые хосты для конфигурации «авто»

В **Серверы → Автохосты** выберите страну, DNS-пул и его хост Remnawave с нужным inbound, портом и транспортом. Нажмите **Подготовить 10 автохостов** для каждой страны. DNS Guard создаст включённые скрытые хосты `dns-guard-auto-de-01`…`dns-guard-auto-de-10` и `dns-guard-auto-fi-01`…`dns-guard-auto-fi-10`. Для создания нужны права записи хостов в Remnawave, для публикации — права записи DNS в выбранной зоне Cloudflare. Пользователям «авто» нужен доступ к inbound автохостов через их сквады.

Один раз подключите хосты к действующему шаблону подписки «авто» типа XRAY_JSON. Добавьте эту группу в массив `remnawave.injectHosts` и добавьте `dns-guard-auto-` в `routing.balancers[].selector` нужного балансировщика и `subjectSelector` его `observatory` или `burstObservatory`. Для отдельных балансировщиков Германии и Финляндии используйте префиксы `dns-guard-auto-de-` и `dns-guard-auto-fi-`. Оставьте в балансировщике действующие точки входа на время заполнения резерва. Проверьте состав «авто» в тестовой подписке и обновите подписки клиентов один раз, чтобы они получили все зарезервированные адреса. [Директива injectHosts в документации Remnawave](https://docs.rw/learn/xray-json-advanced/)

```json
{
  "selector": {
    "type": "remarkRegex",
    "pattern": "^dns-guard-auto-(de|fi)-(0[1-9]|10)$"
  },
  "selectFrom": "HIDDEN",
  "useHostRemarkAsTag": true
}
```

DNS Guard сразу добавляет каждому слоту тег `AUTO_CHEAP_NODE` или значение из `SERVER_ORDER_AUTO_HOST_TAG`. Повторная подготовка добавляет этот тег к существующим слотам и сохраняет остальные теги. Если шаблон использует `tagRegex`, выберите по нему скрытые хосты с этим тегом.

При заказе UpCloud или Virtua.Cloud в настроенной стране и пуле DNS Guard резервирует свободный слот. Для заказа выберите профиль Remnawave исходного хоста. При первоначальной настройке слот создаётся без записи DNS. После успешных проверок DNS Guard публикует IP в DNS-пуле, добавляет тег слоту, если он отсутствует, и публикует CNAME слота на индивидуальный домен ноды. При штатной автозамене DNS Guard переключает A-запись этого домена на новый IP. Автохост и его параметры подключения сохраняются, поэтому клиентские подписки при смене IP обновлять не нужно.

Каждый занятый слот рассчитан на один сервер. Для заказа при заполненных десяти слотах сначала освободите слот либо используйте автозамену существующей ноды. Отмена заказа или удаление цели из DNS Guard освобождает слот. Если CNAME уже публиковался, он сохраняется до успешной проверки нового сервера, назначенного этому слоту.

### Два отдельных плейбука

Для ручных привязок также доступны `REPLACEMENT_ANSIBLE_INSTALL_PLAYBOOK` и `REPLACEMENT_ANSIBLE_TUNING_PLAYBOOK`. Положите плейбуки в `REPLACEMENT_HOST_DIR`, укажите их пути внутри контейнера в `.env` и оставьте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR` и `REPLACEMENT_ANSIBLE_REPO_DIR` пустыми. Оба плейбука должны обрабатывать группу `all` или хост `replacement` и поддерживать повторный запуск через SSH на порту 22. Доступны переменные `dns_guard_node_uuid`, `dns_guard_replacement_ip` и `dns_guard_node_vars`. Для этого режима формат файлов `<uuid>.json` остаётся произвольным объектом переменных. [Переменные окружения](../.env.example)

### Добавление заказанных нод в селектор «Авто» по тегу

Для пулов без зарезервированных автохостов задайте в `.env` `SERVER_ORDER_AUTO_HOST_TAG=AUTO_CHEAP_NODE` или тег из `tagRegex` вашего шаблона XRAY_JSON. После успешной установки и проверки DNS Guard создаст скрытый хост с доменом ноды и этим тегом. Для каждого заказа нужен один включённый видимый хост Remnawave с адресом пула и выбранным inbound. DNS Guard копирует его параметры подключения и ограничения доступа. Токен Remnawave должен разрешать создание, изменение и удаление хостов.

Новый хост появится при обновлении клиентской подписки. При автозамене DNS Guard обновит IP за тем же доменом. Если при удалении заказа выбрано удаление из Remnawave, DNS Guard удалит созданный для заказа автохост. [Настройка `injectHosts`](https://docs.rw/learn/xray-json-advanced/)

### Заказ в Virtua.Cloud

Откройте **Серверы → Заказы серверов → Логи** в карточке нужного заказа. Журнал показывает время смены этапов, попытки создания и ошибки. Для заказов, созданных до обновления, первая запись содержит последний сохранённый этап и доступную на тот момент ошибку.

Сохраните API-токен Virtua.Cloud в **Настройках → Интеграции → Хостинги и Ansible**. В разделе **Серверы** нажмите **Заказать сервер Virtua.Cloud**. DNS Guard загружает почасовые тарифы аккаунта и показывает цену за час и ориентир за месяц без НДС. Оплата списывается с предоплаченного баланса по почасовому тарифу.

Как и для заказа в UpCloud, нужны настройки Ansible, подключённые Cloudflare и Remnawave, шаблон домена пула и доступный по HTTPS `PUBLIC_ORIGIN`. После подтверждения заказа DNS Guard создаёт VPS с Debian 13. Скрипт Virtua.Cloud настраивает вход по ключу Ansible и регистрирует публичный SSH-ключ VPS. Затем DNS Guard регистрирует узел в Remnawave, запускает плейбук и включает узел в DNS-пул после успешных проверок.

### Автозамена Virtua.Cloud

1. Сохраните API-токен в **Настройках → Интеграции → Хостинги и Ansible**. Для автозамены токену нужны заказ и удаление VPS, чтение серверов и их IP-адресов, создание и удаление установочных скриптов. Используются те же Ansible, Cloudflare, Remnawave и регистрация SSH-ключа по HTTPS, что и для заказа нового сервера.
2. В разделе **Автозамена → Привязки узлов** откройте узел пула. Для существующего VPS выберите Virtua.Cloud, укажите UUID VPS и UUID его ноды Remnawave, выберите локацию, почасовой тариф и тип ноды. Укажите отдельный домен ноды в зоне Cloudflare этого пула. DNS Guard создаст A-запись для свободного имени или переключит единственную DNS-only A-запись со старого IP. Для узла, заказанного через DNS Guard, привязка уже заполнена данными заказа. Если тариф изменился, выберите его актуальный вариант.
3. Разрешите платный заказ и удаление старого VPS, сохраните привязку и включите автоматизацию пула. DNS Guard сверит IPv4 VPS с адресом узла в пуле. В Remnawave у этой ноды должен быть указан тот же IPv4 или выбранный домен ноды.

После подтверждённой блокировки DNS Guard заказывает новый VPS на Debian 13 с чистым диском, проверяет его SSH-ключ и запускает Ansible. Используются прежние нода Remnawave и домен ноды. Новый IP публикуется в DNS-пуле после успешных проверок. После истечения TTL DNS Guard повторно проверяет доступность нового IP и переключение DNS и Remnawave, затем удаляет старый VPS вместе с диском. До удаления оба сервера могут тарифицироваться одновременно.

Если ответ на заказ потерялся, DNS Guard ищет VPS по имени `dns-guard-<ID операции>`. Перед разрешением повторного создания проверьте в Virtua.Cloud список серверов и ожидающие заказы. [Документация API Virtua.Cloud](https://manager.virtua.cloud/docs/api)

## Какие серверы UpCloud подходят

Поддерживаются отдельные VM UpCloud с одним обычным публичным IPv4 по DHCP, доступным действующим тарифом или конфигурацией custom и приватными постоянными дисками, принадлежащими этой VM. При пересоздании сохраняются зона, CPU, память, тариф, имя, порядок дисков и поддерживаемые настройки VM. Новая VM получает диски прежнего сервера вместе с ОС и данными. Гостевая ОС должна поднимать сеть по DHCP с новым MAC. Ansible проверяет ключ SSH-хоста через постоянный псевдоним ноды. Если cloud-init при смене instance ID генерирует новый ключ, проверьте его через консоль UpCloud и обновите `known_hosts` перед повтором этапа Ansible.

Автозамена управляет IPv4. Если предусмотрены стандартные дополнительные интерфейсы IPv6 или utility, UpCloud выделит для них новые адреса. Учитывайте это для серверов с отдельными AAAA-записями или сервисами, привязанными к внутреннему IP. Предварительная проверка останавливает замену при конфигурации, которую адаптер не умеет воспроизвести, в том числе при сложной сетевой топологии, общих дисках и пользовательских правилах облачного firewall. Нода Remnawave должна иметь адрес, равный IP цели. Одна привязка соответствует одному серверу, ноде и цели DNS Guard.

## Ход замены UpCloud

- Свежая неудачная серия хотя бы одного работоспособного чекера должна удовлетворять порогу пула. Для старта важен непрерывный интервал. Восстановление, устаревшие данные, пауза, изменение привязки или перезапуск backend сбрасывают незавершённый отсчёт.
- Перед удалением DNS Guard проверяет доступ к DNS и панели, соответствие UUID и IP, параметры VM, диски и входные данные Ansible. Сохранённое описание VM и текущий этап записываются в базу. DNS Guard останавливает и удаляет VM, сохраняя её диски. UpCloud освобождает старый IPv4 при удалении VM согласно её политике `release`.
- После подтверждения удаления DNS Guard создаёт VM с прежними дисками и меткой `dns-guard-replacement=<ID операции>`. UpCloud автоматически назначает ей IPv4. DNS Guard проверяет, что адрес изменился, выполняет настройку через Ansible и обновляет адрес существующей ноды Remnawave. Старые результаты проверок сбрасываются.
- Чекеры проверяют новый IP с профилем пула. После успешной серии у всех доступных чекеров DNS Guard обновляет хосты Remnawave с явным прежним IP и единственной привязанной нодой, публикует новую A-запись и подтверждает удаление старой. Хосты с доменным именем используют тот же DNS-пул. После истечения TTL прежней A-записи приложение ещё раз проверяет, что старый IP отсутствует в DNS, и сохраняет новый UUID сервера в привязке. Операции, начатые по схеме с резервированием IPv4, на этом этапе освобождают зарезервированный адрес в UpCloud.

## Пауза и восстановление

Пауза пула или выключение автозамены приостанавливает начатую замену между этапами. Текущий внешний запрос или плейбук может успеть завершиться. Для продолжения включите пул и автозамену. Изменение привязки, удаление цели и ручная смена IP доступны после завершения начатого удаления и восстановления VM.

После перезапуска backend продолжает уже начатую замену с сохранённого этапа. При ошибке Ansible проверьте показанный этап, SSH-ключ хоста, доступ пользователя и входные файлы. Приложение повторяет этап автоматически. Если новый IP не проходит проверки, операция остаётся на этапе проверки, а подробности доступны в карточке узла пула.

Если UpCloud принял создание VM, но ответ потерялся, DNS Guard ищет её по метке операции и сверяет диски и конфигурацию. При неоднозначном результате он продолжает поиск. Если сервер с меткой отсутствует, исходные диски свободны и запрос в UpCloud завершился без создания VM, проверьте журнал действий в панели UpCloud. После проверки администратор может разрешить повторное создание в истории операции.
