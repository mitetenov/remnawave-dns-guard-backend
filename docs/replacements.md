# Автозамена серверов UpCloud

Раздел **Автозамена** заменяет привязанный сервер, когда DNS Guard пять минут подряд подтверждает блокировку его публичного IPv4. Отсчёт начинается после достижения порога ошибок пула и исключения A-записи. Защищённая последняя A-запись тоже подходит. Для каждого узла требуется явное разрешение на удаление сервера. После обновления приложения все существующие узлы начинают с выключенной автозаменой.

## Ansible для заказов серверов

Образ backend содержит плейбуки для обычных нод (`nodes`) и нод за CDN (`nodes_wl`), их роли, файлы развёртывания и коллекции. При сборке они загружаются из зафиксированной ревизии основной ветки `mitetenov/ansible`. Для заказов DNS Guard формирует inventory с одной нодой, подставляет её домен и ключ Remnawave. Приватный SSH-ключ и настройки групп подключаются с машины развёртывания. Встроенный комплект пропускает установку Alloy, поскольку исходный шаблон настроен для конкретной установки Grafana. [Ревизия Ansible в образе](https://github.com/mitetenov/ansible/tree/d08132cf664ed60174292e09565342dda0e267fb)

1. Рядом с `docker-compose.yaml` создайте `replacement/group_vars`. Положите приватный SSH-ключ входа в `replacement/ssh_key`. Backend работает под UID 10001, которому нужны проход по каталогам и доступ на чтение файлов. Для SSH-ключа нужны права `0600` или `0400` и вход без запроса пароля. По умолчанию используется `root`. Для другого пользователя задайте `REPLACEMENT_ANSIBLE_SSH_USER` в `.env` и настройте повышение привилегий на нодах.

2. Создайте `replacement/group_vars/all.yml` с общими параметрами. Подставьте свой email для Certbot и сверьте настройки nginx с профилем Remnawave.

   ```yaml
   node_initial_ssh_port: 22
   node_ssh_listen_port: 22222
   stack_project_src: /opt/remnawave-node
   stack_files_src: "{{ playbook_dir }}/../files/nodes"
   nginx_node_listen: "127.0.0.1:4321 ssl proxy_protocol"
   nginx_acme_webroot: /var/www/certbot
   nodes_certbot_enabled: true
   ssl_certbot_email: admin@example.com
   ssl_certbot_domains:
     - "{{ nginx_node_domain }}"
   ssl_fullchain_path: "/etc/letsencrypt/live/{{ nginx_node_domain }}/fullchain.pem"
   ssl_privkey_path: "/etc/letsencrypt/live/{{ nginx_node_domain }}/privkey.pem"
   ```

   Для CDN создайте `replacement/group_vars/nodes_wl.yml`. Укажите XHTTP path и порт, настроенные в вашем профиле Remnawave.

   ```yaml
   stack_nodes_nginx_default_template: conf/default-wl.conf.j2
   nginx_node_xhttp_path: /your-xhttp-path/
   nginx_node_xhttp_upstream: 127.0.0.1:8443
   ```

3. Положите `docker-compose.replacements.yaml` из той же версии проекта рядом с `docker-compose.yaml`. Он монтирует `./replacement` только для чтения. Добавьте в `.env` строку `COMPOSE_FILE=docker-compose.yaml:docker-compose.replacements.yaml`, чтобы обычный `docker compose up -d` и обновления загружали оба файла. [Дополнительный файл Compose](../docker-compose.replacements.yaml)

   ```sh
   docker compose config --quiet
   docker compose up -d
   ```

При обновлении с ранее смонтированного репозитория скопируйте настройки групп в `replacement/group_vars` или задайте `REPLACEMENT_ANSIBLE_GROUP_VARS_DIR=/run/dns-guard/replacement/ansible/inventory/group_vars`. Чтобы использовать плейбуки из образа, удалите `REPLACEMENT_ANSIBLE_REPO_DIR` из `.env` и обновите дополнительный файл Compose. Если этот же внешний репозиторий нужен для ручных привязок, задайте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR=/run/dns-guard/replacement/ansible`. Чтобы использовать внешние плейбуки для обоих режимов, оставьте `REPLACEMENT_ANSIBLE_REPO_DIR` с путём к смонтированному репозиторию.

## Автозамена нод с ручной привязкой

Для ранее установленных нод нужен внешний inventory с параметрами конкретных хостов. Заказанные через DNS Guard ноды получают автозамену на основе настроек групп и сохранённого публичного ключа хоста.

1. На машине развёртывания подготовьте рабочую копию рядом с `docker-compose.yaml`. Установите коллекции в каталог этой копии с помощью `ansible-galaxy` из Ansible Core. В `.env` задайте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR=/run/dns-guard/replacement/ansible`.

   ```sh
   mkdir -p replacement/node_vars
   git clone https://github.com/mitetenov/ansible.git replacement/ansible
   git -C replacement/ansible checkout --detach d08132cf664ed60174292e09565342dda0e267fb
   (cd replacement/ansible && ansible-galaxy collection install -r requirements.yml -p ./collections)
   ```

2. Для каждой ранее установленной ноды, которую вы подключаете вручную, создайте `replacement/node_vars/<uuid-ноды-remnawave>.json`. Укажите UUID в нижнем регистре. В качестве `inventory_hostname` используйте имя узла из `inventory/hosts.yml`. Например, файл для ноды, зарегистрированной как `finland-01`, выглядит так.

   ```json
   {"inventory_hostname": "finland-01"}
   ```

   | Группа в inventory | Плейбук |
   | --- | --- |
   | `nodes` | `playbooks/nodes.yml` |
   | `nodes_wl` | `playbooks/nodes-wl.yml` |

   Домен и параметры узла берутся из переменных хоста и группы. Новый IPv4 подставляется на время запуска. Для последующих ручных запусков этого inventory используйте актуальный адрес узла. Роль `stack_nodes` сохраняет существующий `/opt/remnawave-node/.env` на перенесённом диске. Если его предстоит создать, задайте `stack_node_secret_key` или `stack_nodes_env_content` в настройках ноды.

3. Для ранее установленной ноды создайте `replacement/known_hosts` с проверенным публичным **ключом хоста** исходной VM. Вместо имени сервера укажите UUID ноды Remnawave. Эта привязка позволяет проверить тот же ключ на новом IP при переключении SSH между портами 22222 и 22.

   ```text
   <uuid-ноды-remnawave> ssh-ed25519 <публичный-ключ-хоста-в-base64>
   ```

4. Подключите `./replacement` через дополнительный файл Compose и примените настройки, как описано в предыдущем разделе. В **Настройках** подключите Cloudflare и Remnawave. Для Cloudflare нужны чтение зоны и изменение DNS. Для Remnawave нужны чтение нод и хостов, изменение адреса ноды и хостов с явным IP. В **Автозамене** сохраните API-токен UpCloud с доступом к VM, дискам, планам, интерфейсам, правилам firewall и управлению публичными IP. Для целевого узла укажите UUID VM и ноды, разрешите замену и включите автоматизацию пула.

Если на узле включён Certbot, плейбук использует сертификаты с перенесённого диска. Для выдачи или продления через HTTP-01 домен `nginx_node_domain` должен вести к доступному ACME webroot в момент запуска роли `ssl`. Это важно для индивидуального домена ноды или отдельного CDN origin. Смена A-записи пула происходит после Ansible и успешных проверок.

## Заказ нового сервера

В боковом меню откройте **Серверы**. В настройках нужного DNS-пула задайте шаблон индивидуального домена ноды. У пула должны быть профиль проверок DNS Guard и соответствующий хост в Remnawave. Шаблон должен порождать домен в той же зоне Cloudflare. Переменная `{n}` обязательна и даёт порядковый номер, `{country}` подставляет код страны UpCloud в нижнем регистре, `{pool}` подставляет полное имя пула. Например, `{country}-{n}.{pool}` для пула `eu.example.com` и Германии даёт `de-01.eu.example.com`. Шаблон можно изменить для следующих заказов. Пустое значение убирает пул из списка для новых заказов.

1. Нажмите **Заказать сервер** и выберите страну с конкретной зоной. DNS Guard читает публичные локации из UpCloud и загружает тарифы для выбранной зоны. Для каждого тарифа показываются CPU, память, диск и почасовая цена в валюте аккаунта. Поддерживаются постоянные VM с включённым диском и публичным IPv4. Доступность ресурсов UpCloud подтверждает при создании.
2. Выберите DNS-пул, тип ноды (`nodes` или `nodes_wl`) и существующий профиль Remnawave. Нода получает входящие подключения выбранного профиля. Профиль должен иметь хотя бы одно подключение, назначенное хосту этого пула в панели.
3. Проверьте выбор и подтвердите платный заказ. DNS Guard повторно проверит цену и конфигурацию тарифа до отправки запроса. В истории заказа можно следить за этапами и отменить заказ до отправки запроса на создание VM.
4. DNS Guard создаёт VM из публичного образа Debian 13, получает её публичный SSH-ключ через HTTPS и создаёт индивидуальную A-запись для домена ноды. Затем регистрирует ноду в Remnawave и запускает плейбук с выбранными группой и доменом. Публичный адрес пула получает новый IP после успешных проверок. В подходящих хостах Remnawave сохраняются существующие назначения.
5. После завершения DNS Guard включает автозамену для созданного сервера. Для работы замены должна быть включена автоматизация самого пула. При пересоздании VM индивидуальное имя сохраняется, а его A-запись переводится на новый IP до запуска Ansible.

Для первого заказа подключите каталог настроек групп и SSH-ключ входа. На внешнем HTTPS-адресе `PUBLIC_ORIGIN` для новой VM должен быть доступен `POST /api/server-orders/<uuid>/enroll`. Маршрут принимает одноразовую регистрацию с токеном конкретного заказа. Если внешний прокси требует дополнительный вход, откройте только этот маршрут для регистрации. Доступ к остальным операциям управления по-прежнему требует сессию администратора.

Если в истории заказа появилась ошибка `new node orders require REPLACEMENT_ANSIBLE_REPO_DIR`, обновите образ backend и дополнительный файл Compose, затем подключите настройки групп и SSH-ключ. Из каталога установки выполните `docker compose up -d --no-deps backend`. Заказ на этапе «Проверка заказа» продолжится автоматически после исправления.

Для заказа токену UpCloud также нужен доступ к спискам зон, тарифов, цен и публичных образов, к валюте аккаунта и созданию облачных серверов и дисков с метками. Токен Remnawave должен позволять читать профили и ключ установки ноды, создавать ноды и обновлять назначения хостов. Индивидуальная A-запись создаётся без проксирования и помечается идентификатором заказа. При конфликте домена проверьте историю до повторного заказа. Если ответ при создании VM потерян, DNS Guard продолжает искать тот же сервер. Доступное в истории повторное создание требует проверки отсутствия сервера в UpCloud.

### Два отдельных плейбука

Для ручных привязок также доступны `REPLACEMENT_ANSIBLE_INSTALL_PLAYBOOK` и `REPLACEMENT_ANSIBLE_TUNING_PLAYBOOK`. Подключите свои плейбуки через собственный файл Compose и оставьте `REPLACEMENT_ANSIBLE_MANUAL_REPO_DIR` и `REPLACEMENT_ANSIBLE_REPO_DIR` пустыми. Оба плейбука должны обрабатывать группу `all` или хост `replacement` и поддерживать повторный запуск через SSH на порту 22. Доступны переменные `dns_guard_node_uuid`, `dns_guard_replacement_ip` и `dns_guard_node_vars`. Для этого режима формат файлов `<uuid>.json` остаётся произвольным объектом переменных. [Переменные окружения](../.env.example)

## Какие серверы подходят

Поддерживаются отдельные VM UpCloud с одним обычным публичным IPv4 по DHCP, доступным действующим тарифом или конфигурацией custom и приватными постоянными дисками, принадлежащими этой VM. При пересоздании сохраняются зона, CPU, память, тариф, имя, порядок дисков и поддерживаемые настройки VM. Новая VM получает диски прежнего сервера вместе с ОС и данными. Гостевая ОС должна поднимать сеть по DHCP с новым MAC. Ansible проверяет ключ SSH-хоста через постоянный псевдоним ноды. Если cloud-init при смене instance ID генерирует новый ключ, проверьте его через консоль UpCloud и обновите `known_hosts` перед повтором этапа Ansible.

Автозамена управляет IPv4. Если предусмотрены стандартные дополнительные интерфейсы IPv6 или utility, UpCloud выделит для них новые адреса. Учитывайте это для серверов с отдельными AAAA-записями или сервисами, привязанными к внутреннему IP. Предварительная проверка останавливает замену при конфигурации, которую адаптер не умеет воспроизвести, в том числе при сложной сетевой топологии, общих дисках и пользовательских правилах облачного firewall. Нода Remnawave должна иметь адрес, равный IP цели. Одна привязка соответствует одному серверу, ноде и цели DNS Guard.

## Ход замены

- Свежая неудачная серия хотя бы одного работоспособного чекера должна удовлетворять порогу пула. Для старта важен непрерывный интервал. Восстановление, устаревшие данные, пауза, изменение привязки или перезапуск backend сбрасывают незавершённый отсчёт.
- Перед удалением DNS Guard проверяет доступ к DNS и панели, соответствие UUID и IP, параметры VM, диски и входные данные Ansible. Сохранённое описание VM и текущий этап записываются в базу. UpCloud резервирует старый IPv4, останавливает сервер и удаляет его, сохраняя диски.
- DNS Guard создаёт VM с меткой `dns-guard-replacement=<ID операции>`, получает другой IPv4, выполняет настройку через Ansible и меняет адрес существующей ноды Remnawave. Старые результаты проверок сбрасываются.
- Чекеры проверяют новый IP с профилем пула. После успешной серии у всех доступных чекеров DNS Guard обновляет хосты Remnawave с явным прежним IP и единственной привязанной нодой, публикует новую A-запись и подтверждает удаление старой. Хосты с доменным именем используют тот же DNS-пул. После истечения TTL прежней A-записи приложение ещё раз проверяет, что старый IP отсутствует в DNS, освобождает его в UpCloud и сохраняет новый UUID сервера в привязке.

## Пауза и восстановление

Пауза пула или выключение автозамены приостанавливает начатую замену между этапами. Текущий внешний запрос или плейбук может успеть завершиться. Для продолжения включите пул и автозамену. Изменение привязки, удаление цели и ручная смена IP доступны после завершения начатого удаления и восстановления VM.

После перезапуска backend продолжает уже начатую замену с сохранённого этапа. При ошибке Ansible проверьте показанный этап, SSH-ключ хоста, доступ пользователя и входные файлы. Приложение повторяет этап автоматически. Если новый IP не проходит проверки, операция остаётся на этапе проверки, а подробности доступны в карточке узла пула.

Если UpCloud принял создание VM, но ответ потерялся, DNS Guard ищет её по метке операции и сверяет диски и конфигурацию. При неоднозначном результате он продолжает поиск. Если сервер с меткой отсутствует, исходные диски свободны и запрос в UpCloud завершился без создания VM, проверьте журнал действий в панели UpCloud. После проверки администратор может разрешить повторное создание в истории операции.
