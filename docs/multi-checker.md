# Несколько чекеров

Каждый чекер проверяет каждый включённый IP во всех пулах с сохранённым профилем, включая исключённые из DNS адреса. Регистрация происходит при первом авторизованном опросе. Список разрешённых ID, количество чекеров и привязки к пулам в DNS Guard не настраиваются.

На новой ноде задайте только окружение агента:

```dotenv
CONTROL_PLANE_URL=https://guard.example.com
AGENT_TOKEN=<тот же секрет, что у backend>
AGENT_ID=ru-provider-city-2
```

`AGENT_ID` должен быть уникальным и стабильным. Два процесса с одинаковым ID считаются одним чекером и не обеспечивают независимые проверки. Токен даёт право регистрировать чекеры и отправлять результаты: передавайте его только доверенным серверам. Новый токен для каждой ноды, перезапуск backend и изменения пулов не нужны. Существующий протокол агента сохранён; обновлять бинарник агента для нескольких чекеров не требуется. Требования профилей к версии агента (XHTTP extra >=1.1.0, ALPN >=1.2.0) сохраняются.

## Решения по DNS

- У каждой пары «чекер + IP» отдельные расписание, результат и последовательные счётчики. Проверка от одного чекера не блокирует проверку того же IP другими. У одного чекера максимум четыре незавершённых задания.
- `failure_threshold` последовательных ошибок **хотя бы одного** здорового чекера достаточно для исключения. Ошибки разных чекеров не складываются, успехи другого чекера их не сбрасывают. Для немедленного исключения после первой ошибки установите порог 1.
- Возврат требует `recovery_threshold` последовательных успехов **каждого активного** чекера. Новая нода сначала должна выполнить проверки; отсутствие результата, неподдерживаемый профиль или неопределённая проверка не считаются успехом.
- Активен чекер с успешной прямой контрольной связью и heartbeat не старше 90 секунд. Чекеры с проблемами контроля или без связи остаются видны, но временно не участвуют в решениях. Их исчезновение не считается ошибкой IP. Если нет активных чекеров, автоматические изменения DNS по проверкам не выполняются.
- Результат действителен менее `max(180 секунд, 3 × интервал пула)`. Свежий отказ имеет приоритет над отсутствующими результатами других чекеров; для состояния «Доступен» нужны свежие успешные результаты всех активных чекеров.
- После разрыва heartbeat или контрольной связи, просроченной аренды и неопределённой пробы серия соответствующего чекера начинается заново. Серии остальных чекеров сохраняются. При смене профиля/IP и ручном включении/отключении сбрасываются проверки всех чекеров этого IP. Внешнее изменение DNS также требует новых серий.
- Сохранены защита последней фактической A-записи, ручное отключение, пауза автоматики, одноразовые задания и проверка версии профиля. Отложенные автоматические операции повторно проверяют актуальные результаты всех чекеров перед исполнением.

## Панель и API

В настройках показаны ID, версия, последняя связь и отдельный статус каждой ноды: `online`, `control_unhealthy`, `offline`. В шапке — количество готовых и общее количество зарегистрированных чекеров. У каждого IP раскрывается список результатов и серий всех чекеров. Сводный счётчик ошибок — максимум среди свежих активных чекеров, успехов — минимум среди всех активных чекеров (0 при отсутствии свежей проверки).

`GET /api/agents` возвращает список `{id,version,last_seen,healthy,status}`. Те же данные доступны в `agents` у `/api/settings` и `/api/overview`, вместе с `agents_total` и `agents_healthy`. Старое `agent_healthy` означает наличие хотя бы одного готового чекера, `agent_last_seen` — самую недавнюю связь.

Target дополнительно возвращает `checkers_active`, `checkers_checked` и `checks:[{agent_id,fresh,failures,successes,last_checked_at,last_latency_ms,last_error,outcome}]`. `outcome` — `true`, `false` либо `null` для отсутствующего/неопределённого результата. `probe_fresh` обозначает достаточное актуальное свидетельство: свежий отказ любого чекера либо свежие результаты всех активных чекеров.

## Обновление

Нужно однократно обновить backend и frontend. Миграция SQLite автоматическая: создаётся `target_checks`, старый результат переносится в пару с последним проверявшим агентом, а ограничение аренды меняется с IP на пару «IP + чекер». Профили, IP, настройки DNS и секреты сохраняются. После миграции остальные чекеры самостоятельно создадут свои проверки. Новые таблицы используют каскадное удаление при удалении IP/пула. Старый backend нельзя запускать на новой схеме: его запрос регистрации агента и глобальные счётчики несовместимы. Для отката используйте резервную копию БД до обновления.

Проверки политики выполняются изолированными unit-тестами без внешних сервисов. Дополнительно изменение проверено локальным одноразовым runtime-прогоном: отдельная временная SQLite, HTTP handler и полностью подменённый Cloudflare transport. Производственная БД и реальные DNS-записи при разработке не используются.
