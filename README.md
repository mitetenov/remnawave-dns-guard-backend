# Remnawave DNS Guard backend

Панель управления Cloudflare A round robin с проверкой VLESS из России. Каждый подключённый RU-чекер независимо проверяет каждый публичный IPv4 через Xray, сохраняя SNI и параметры общего inbound. После серии ошибок панель исключает адрес из DNS, продолжает его проверять и возвращает после восстановления. Недоступный сервер тоже даёт ошибку проверки.

Это самостоятельное Docker-приложение: React/nginx → Go → SQLite; RU-чекеры запускаются на отдельных серверах. Remnawave используется только для чтения узлов и хостов. В этой версии поддерживаются VLESS TCP/XHTTP и REALITY/TLS, IPv4 и DNS-only A-записи. Не поддерживаются произвольные Xray-конфиги, AAAA и Cloudflare Proxy для адресов пула.


Репозиторий содержит Go/SQLite, API-контракт, тесты и Compose панели.
[Фронтенд](https://github.com/mitetenov/remnawave-dns-guard-frontend) и
[RU-агент](https://github.com/mitetenov/remnawave-dns-guard-agent) находятся в отдельных репозиториях.
Для запуска используются готовые образы Docker Hub. На сервере достаточно `docker-compose.yaml` и `.env`; клонировать репозитории и устанавливать Go/Node.js не требуется.

## Агенты и маршруты проверок

Счётчик вкладки «Агенты» показывает общее число зарегистрированных агентов, как счётчик DNS-пулов. Раздел «Агенты» показывает всех подключённых агентов; офлайн-регистрации доступны отдельным фильтром. На странице агента два независимых переключателя: «Напрямую» (агент → VLESS-нода) и «Через SOCKS5» (агент → SOCKS5 → VLESS-нода). Оба маршрута выполняют полноценные Xray-пробы; отказ любого из них проваливает общий чек. Сбой самого SOCKS5 пропускает только этот маршрут и сохраняет прямой результат. Все пропущены — нет достоверного результата; оба выключены — пробы на паузе.

Для SOCKS5 нужен агент **1.4.0+**. В поле панели введите только `IP:PORT:LOGIN:PASS`, например `192.0.2.10:1080:login:password`, затем включите маршрут. Форма принимает IPv4 и обязательные логин/пароль, сама преобразует ввод в SOCKS5 URL и экранирует учётные данные. API и агент сохраняют поддержку SOCKS5 URL, включая socks5h/IPv6 и приватные адреса. Выключение SOCKS5 сохраняет настройки; удаление URL выключает только этот маршрут. Связь с панелью остаётся прямой. Настройки применяются при следующем poll без перезапуска.

Кнопка «Проверить прокси» выполняет HTTPS через SOCKS5 с выбранного агента, включая на паузе. Агент **1.5.0+** позволяет проверить введённые данные до сохранения: это отдельное задание, которое не меняет рабочий прокси, его состояние и серии VLESS-проверок. Агент 1.4 сохраняет проверку уже сохранённого прокси. Результат, задержка и внешний IP (при ответе Cloudflare trace) видны в панели; тайм-аут — 60 секунд. Поле ввода и сохранённый прокси на странице агента отображаются открытым текстом в формате `IP:PORT:LOGIN:PASS`. В SQLite рабочий URL и адрес отдельного теста зашифрованы с APP_SECRET. Полные данные доступны только в авторизованных ответах страницы агента с `Cache-Control: no-store`; сводки и журналы не содержат учётных данных. Смена настроек отзывает задания и серии только данного агента. Результаты маршрутов доступны отдельно у каждого IP; DNS-пороги и защита последней A сохраняются.

## Что потребуется

- Linux-сервер панели с Docker Engine и Compose v2, существующий HTTPS reverse proxy и отдельный домен, например `guard.example.com`.
- Сервер в России с Docker и исходящим HTTPS, доступом к публичным IP узлов и панели. Агент не открывает входящие порты.
- Cloudflare-зона, полномочия редактирования её DNS и одинаковый работающий inbound/конфиг на всех узлах одного пула.
- Для импорта: адрес Remnawave и отдельный API token с правами только чтения.

DNS-кеши учитывают TTL, поэтому удаление записи не мгновенно переключает всех клиентов. Последний оставшийся A сохраняется даже при его отказе: это защита от пустого DNS, а не гарантия доступности.

Незавершённые DNS-операции сохраняются до обращения к Cloudflare. Если после применения записи ответ потерялся, API может вернуть 502, но операция останется в состоянии «Ожидает подтверждения» и будет повторно проверена через 30 секунд, в том числе после перезапуска. Ручные отключение/удаление в этом состоянии прекращают мониторинг цели и не допускают автоматического возврата. Защита последней A по-прежнему возвращает 409. Проверяйте состояние цели перед повторным действием.

Фоновая сверка DNS выполняется раз в 5 минут и показывает внешние изменения и неизвестные записи. Она не принимает неизвестные IP под управление автоматически. После внешнего удаления управляемой A серии сбрасываются; автоматический возврат требует новых успешных проверок до порога восстановления. Любая proxied A/AAAA того же hostname блокирует изменение до устранения конфликта оператором.

Панель отдельно показывает свежесть пробы и подтверждение DNS. Результат устаревает при отсутствии здорового heartbeat агента более 90 секунд или после max(180 секунд, 3 × интервал пула) без новой пробы. Потеря свежести не считается отказом узла. Медленные запросы внешних интеграций не удерживают блокировку приёма heartbeat и результатов.

При обновлении с первой версии потребуется повторный вход: старые сессии без версии учётных данных отзываются. Дальше смена `ADMIN_USERNAME` или `ADMIN_PASSWORD` отзывает прежние сессии, а обычный перезапуск с теми же значениями сохраняет их. Обновляйте frontend и backend согласованно; перед обновлением сохраните SQLite и `APP_SECRET` по инструкции резервного копирования.

## Запуск панели

Для новой установки в отдельном каталоге скачайте только Compose и пример настроек:

```sh
umask 077
mkdir -p /opt/remnawave-dns-guard
cd /opt/remnawave-dns-guard
curl -fsSLo docker-compose.yaml https://raw.githubusercontent.com/mitetenov/remnawave-dns-guard-backend/main/docker-compose.yaml
curl -fsSLo .env https://raw.githubusercontent.com/mitetenov/remnawave-dns-guard-backend/main/.env.example
chmod 600 .env
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 24
```

Запишите **разные** результаты первых двух команд генерации в `APP_SECRET` и `AGENT_TOKEN`, третий можно использовать как `ADMIN_PASSWORD`. Заполните `ADMIN_USERNAME`. Не вставляйте эти значения в переписку, git или URL. Значения секретов должны содержать минимум 32 символа; backend проверяет обязательные настройки при запуске. Пример не содержит рабочих учётных данных. Для существующей установки сохраняйте прежний `.env`, не скачивая его поверх настроек.

Установите `PUBLIC_ORIGIN=https://guard.example.com`: точный origin браузера без завершающего `/` и без пути. Для HTTPS оставьте `COOKIE_SECURE=true`. Backend получает настройки из `.env` через `env_file`; значения приложения не перечисляются в Compose. Путь файла считается относительно `docker-compose.yaml`. Оставьте `DATABASE_PATH=/data/guard.db`, чтобы база находилась в подключённом томе, и `LISTEN_ADDR=:8000` для связи с nginx. Адрес и host-порт панели (`UI_BIND_ADDRESS`, `UI_PORT`) Compose также читает из `.env`; фронтенду отдельный API URL не нужен.

```sh
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:8080/api/health
```

Панель привязана к `127.0.0.1:8080`; backend не публикует порт на хосте. HTTPS завершается вашим reverse proxy. SQLite хранится в именованном томе `remnawave-dns-guard_guard-data`, путь внутри backend — `/data/guard.db`. Оставьте ровно один экземпляр backend: SQLite и DNS reconciliation рассчитаны на такую схему.

Для осознанной локальной разработки можно установить `PUBLIC_ORIGIN=http://localhost:8080` и `COOKIE_SECURE=false`, затем открыть именно этот адрес. Для удалённой панели нужен HTTPS. Не публикуйте HTTP порт в Интернет.

## Reverse proxy

Пример для nginx **на том же хосте**; замените домен и пути сертификата. Для Docker-прокси `127.0.0.1` означает сам контейнер: подключите его к сети панели и направьте трафик на `frontend:80`, либо настройте доступ к хосту отдельно.

```nginx
server {
    listen 80;
    server_name guard.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name guard.example.com;
    ssl_certificate /etc/letsencrypt/live/guard.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/guard.example.com/privkey.pem;
    client_max_body_size 128k;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
```

Сохраняйте `Origin`, Cookie и Authorization. Изменение origin/домена требует обновить `PUBLIC_ORIGIN` и пересоздать backend: `docker compose up -d`. UI использует HttpOnly cookie, SameSite=Strict и проверку origin для изменений. Агент авторизуется отдельным Bearer token. Если добавляете внешнюю авторизацию на proxy, обеспечьте доступ агента к `/api/agent/` без интерактивного браузерного входа; Bearer-проверка приложения должна остаться.

## Интеграции и первый пул

1. Войдите под `ADMIN_USERNAME` / `ADMIN_PASSWORD`, откройте «Настройки».
2. Создайте отдельный [Cloudflare API token](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) с `Zone → DNS → Edit` и `Zone → Zone → Read`. Ограничьте **Zone Resources** только нужной зоной или явным списком зон. Не используйте Global API Key. Введите токен в панели и выполните тест подключения. `DNS Edit` позволяет читать и менять записи, `Zone Read` нужен для выбора зоны.
3. Для импорта создайте Remnawave API token с минимальными scopes `nodes:list` и `hosts:list` (либо read, если установленная версия объединяет права чтения). Используйте API token из панели, не admin login JWT. Не выдавайте write, restart или административные полномочия. Введите HTTPS-адрес панели и токен, проверьте подключение. Проверьте [официальный API установленной версии](https://docs.rw/api/), если названия scopes отличаются. Адаптер сверялся с текущим официальным Remnawave backend 3.4.5 (`GET /api/nodes`, `GET /api/hosts`); подключение к вашей установленной панели требует отдельного теста. Панель DNS Guard не меняет пользователей, узлы, хосты или конфиги Remnawave.
4. Создайте пул: имя, зона, **точный** hostname вроде `vpn.example.com`, TTL (обычно 120), интервал (обычно 60 секунд), пороги ошибок/восстановления (по умолчанию 3/5). Автоматика изначально выключена. TTL применяется к новым и восстановленным записям; существующие/принятые записи сохраняют TTL. Hostname и зону нельзя изменить, пока в пуле есть цели (409); создайте новый пул для другого hostname.
5. Добавьте публичные IPv4 вручную, импортируйте выбранные узлы Remnawave или синхронизируйте существующие A точного hostname. Добавление создаёт либо принимает совпадающую DNS-only запись. Импорт из Remnawave — явное добавление, он тоже меняет DNS. Если узел указан hostname и адрес не определён как публичный IPv4, задайте IP явно. Проверьте импортируемый IP вручную: `node.address` может быть адресом управления, а не клиентским адресом inbound. Proxied A следует предварительно перевести в DNS-only; CNAME не заменяйте автоматически.
6. Сохраните профиль проверки: вставьте VLESS URI работающего клиента, заполните поддерживаемые поля либо откройте «Вставить ссылку на подписку», загрузите HTTPS-подписку и выберите сервер. Поддерживаются текстовые и Base64-списки VLESS; неподдерживаемые серверы показаны с причиной. Подписка загружается один раз: сохраняются только параметры выбранного сервера, без автоматического обновления. Адреса серверов подписки не заменяют IP узлов пула. Если подписка требует HWID, отметьте «Использовать DNS Guard как отдельное устройство» и повторите загрузку. Это может занять один слот устройства в Remnawave; повторы и перезапуски используют тот же идентификатор при сохранении `APP_SECRET`. Для разных доменов подписок идентификаторы различаются. Без этой опции HWID не передаётся. При заполненном лимите освободите слот либо используйте отдельную проверочную подписку. UUID, порт, транспорт, SNI, REALITY public key/short ID, flow, fingerprint и XHTTP path/host/mode/extra должны соответствовать inbound **на каждом узле пула**. Используйте VLESS URI отдельного разрешённого тестового пользователя: список Remnawave hosts сам по себе не даёт клиентские credentials для проб. Один профиль применяется ко всем адресам; при разных конфигурациях создайте разные пулы. URI/UUID содержат секреты. Профиль доступен только на запись; API не возвращает сохранённые секреты в UI.
Для XHTTP поддерживается `extra` из VLESS-ссылки, включая padding, headers, параметры POST и xmux. JSON сохраняется целиком с профилем; его можно проверить и изменить в поле «XHTTP extra (JSON)». Размер — до 16 КиБ. Неизвестные поля и отдельное подключение `downloadSettings` отклоняются, чтобы проверка оставалась привязана к IP узла. Перед использованием `extra` обновите RU-агент до **1.1.0 или новее**, затем backend и frontend: старые агенты не получают такие задания.

Для TLS также импортируется `alpn`, например `h2,http/1.1`; порядок протоколов сохраняется. Его можно изменить в поле «ALPN» или оставить пустым для стандартного поведения Xray. Для профилей с ALPN нужен RU-агент **1.2.0 или новее**: обновите его перед backend/frontend. REALITY не принимает отдельную настройку ALPN.

7. Запустите RU-агент по следующему разделу. Убедитесь, что он виден и его контрольная связь здорова. Нажмите «Проверить сейчас» и дождитесь реальных результатов: при выключенной автоматике проверки работают, DNS автоматически не меняется. Если профиль ещё не задан, кнопка откроет его настройку; «Сохранить и проверить» сохранит профиль и поставит проверку в очередь без включения Guard.
8. После проверки адресов включите автоматику. Для включения нужны цели и сохранённый профиль. Смотрите статусы, счётчики и журнал (хранится до 30 дней и не более 100 000 событий); пустой журнал после создания — нормальное состояние, демонстрационных результатов нет.

Cloudflare/Remnawave токены можно также задать через необязательные переменные `.env` для первоначальной настройки. Сохранённые интеграции и профиль шифруются в SQLite ключом от `APP_SECRET`; токены не возвращаются API и не должны попадать в логи. Сохраните `APP_SECRET` вместе с резервной копией: простая замена ключа не расшифрует старые значения.

## Агенты в России

Поддерживается любое количество чекеров с автоматической регистрацией: каждый проверяет все IP. Достаточно запустить новую ноду с общим токеном и уникальным `AGENT_ID`; настройки DNS Guard менять не нужно. Статусы нод видны в настройках, результаты каждого чекера — у IP. Подробности решений, API и миграции: [несколько чекеров](docs/multi-checker.md).

На RU-хосте клонируйте репозиторий агента; файл `.env` панели ему не нужен:

```sh
git clone https://github.com/mitetenov/remnawave-dns-guard-agent.git
cd remnawave-dns-guard-agent
cp .env.example .env
chmod 600 .env
```

Впишите HTTPS `CONTROL_PLANE_URL` и **тот же** `AGENT_TOKEN`, что у backend. Задайте стабильный уникальный `AGENT_ID`, например `ru-moscow-1`. `CONTROL_URLS` проверяются напрямую, `PROBE_URLS` — через VLESS туннель; можно выбрать подходящие публичные HTTPS адреса с ожидаемым кодом 2xx/3xx. Приватные адреса и переходы к ним не допускаются. `ALLOW_INSECURE_HTTP` оставьте `false`.

```sh
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100 agent
```

Xray включён в образ. Агент адресует VLESS outbound непосредственно проверяемому IP, а не round-robin hostname, сохраняя SNI и ключи. Одновременно выполняется не более четырёх задач. Временные конфиги имеют права `0600`, удаляются после задачи; proxy слушает только loopback внутри контейнера. Панель не передаёт произвольные команды или raw Xray конфиги. Источником истины об агенте служит heartbeat в UI; Docker `healthy` проверяет продвижение цикла опроса и успешный авторизованный poll за последние 180 секунд. Прямая контрольная связь может быть недоступна при работающем poll; это отображается отдельно в UI. Healthcheck не проверяет конкретный узел.

## Как принимаются решения

- Ошибка туннеля, сервера или доступности контрольного HTTPS через туннель считается провалом цели **только при здоровой прямой контрольной связи агента**. Сбой самого агента/его канала не превращает весь пул в недоступный; этот чекер временно не участвует в решениях. Сообщённый control outage аннулирует текущие задания и сбрасывает серии проверок этого агента.
- Серия из `failure_threshold` принятых неудачных проверок хотя бы одного здорового чекера исключает IP. Серии раздельные: успех другого чекера не сбрасывает ошибки. Проверки исключённого адреса продолжаются; для возврата каждый активный чекер должен набрать `recovery_threshold` успехов.
- Защита последнего фактического A действует и для автоматики, и для ручного отключения/удаления. Защищённый отказ виден отдельным статусом. Перед операцией запрашивается текущее DNS, после — проверяется результат. Ошибка Cloudflare не обозначается как успешное изменение.
- Ручное отключение снимает A и выключает мониторинг; адрес **никогда не возвращается автоматически**. Повторное включение — явное действие. Удаление требует подтверждения и удаляет цель, если это безопасно.
- Пауза автоматики оставляет проверки работающими. Она блокирует автоматические изменения DNS; ручные действия остаются доступными. Смена профиля сбрасывает серии и делает старые задания недействительными.
- Задания привязаны к агенту и версии профиля, одноразовые и имеют срок аренды 180 секунд. Для принятия результатов нужен здоровый heartbeat не старше 90 секунд. Повторные, просроченные и чужие результаты не продвигают счётчики. Просроченная задача означает неизвестный результат, не ошибку узла.

Интервал — период планирования, а не строгий SLA. Опрос, очередь задач, таймаут проверки, DNS API и TTL увеличивают фактическое время переключения; 3 ошибки при интервале 60 секунд не обещают ровно 180 секунд. Для больших пулов учитывайте лимит четырёх незавершённых проверок на каждого RU-чекера. Все чекеры проверяют все IP, поэтому их добавление увеличивает число независимых наблюдений, а не делит пул.

## Эксплуатация

```sh
docker compose logs --tail=100 backend frontend
docker compose restart backend
docker compose pull
docker compose up -d
```

Compose ограничивает CPU, память, число процессов и Docker-логи (3 файла по 10 MiB на контейнер). Сервисы перезапускаются после завершения процесса. Docker не перезапускает контейнер лишь из-за статуса `unhealthy`: проверьте журнал и причину отказа. Backend healthcheck показывает HTTP-ответ сервиса, не соединение с Cloudflare, Remnawave или RU.

Не запускайте второй backend на той же БД. Не выполняйте `docker compose down -v`, если хотите сохранить данные. Для обычного выключения используйте `docker compose down`. `ADMIN_PASSWORD` меняется в `.env` с последующим пересозданием backend; после смены выполняйте новый вход. При ротации `AGENT_TOKEN` обновите backend и RU-агент согласованно. Не меняйте `APP_SECRET` без миграции зашифрованных данных.

## Разработка и сборка

Нужен Go 1.27.3. Бэкенд — один статически собранный бинарный файл без Python, libc и shell в runtime. SQLite-драйвер `modernc.org/sqlite` закреплён в `go.mod`/`go.sum`.

```sh
go test -race ./...
go build -o dns-guard-backend ./cmd/dns-guard
# Загрузите свои переменные окружения, затем:
./dns-guard-backend
```

`LISTEN_ADDR` по умолчанию `:8000`; для локального запуска можно задать `127.0.0.1:8000`. Go-модуль допускает нативную разработку на macOS, но Docker-образы поддерживаются и собираются **только для Linux AMD64**. Сборка Docker для ARM завершается ошибкой. Runtime использует UID/GID `10001`, сертификаты CA и записываемый `/data`; проверка здоровья — `/dns-guard --healthcheck`.

Существующая SQLite, Fernet-шифрование настроек/профилей и версия учётных данных совместимы с Python-версией. При сохранённых `APP_SECRET` и учётных данных действующие сессии продолжают работать после обычного обновления. Миграция добавляет отсутствующие колонки. Перед заменой образа сохраните согласованную резервную копию.

## Сборка и CI

Локальная сборка из корня этого репозитория:

```sh
docker build --platform linux/amd64 -t remnawave-dns-guard-backend:local .
```

Dockerfile сначала копирует `go.mod`/`go.sum` и загружает зависимости, затем — только production-код. Изменения тестов и документации не сбрасывают кеш сборки. BuildKit сохраняет кеш компилятора Go между сборками на одном builder; зависимости также остаются обычным слоем, доступным для CI-кеша `type=gha,mode=max`. Cache mounts сами по себе в GitHub layer cache не экспортируются. В scratch стабильные CA/каталоги и часто меняющийся бинарник разделены независимыми `COPY --link` слоями.

Каждый push и pull request запускает изолированные Go unit-тесты с race detector, проверку модулей/форматирования/vet/lint, Compose и production Docker build. Тесты реальной SQLite, отдельно запущенных сервисов и контейнеров удалены.
После всех проверок `main` публикует AMD64-образ
`mitetenov/remnawave-dns-guard-backend` с тегами `latest` и `sha-<полный commit SHA>`.
Pull request не публикует образы; deploy автоматически не выполняется.

Repository variables: `DOCKERHUB_USERNAME`, `DOCKERHUB_IMAGE`.
Repository secret: `DOCKERHUB_TOKEN` с правами Read & Write.
В `docker-compose.yaml` указаны готовые образы backend и frontend с тегом `latest`.
Для обновления выполните `docker compose pull` и `docker compose up -d`.
Для отката замените тег непосредственно в нужном `image:` на `sha-<полный commit SHA>`.
Теги бэкенда и UI относятся к независимым commit SHA.

## Уведомления Telegram

В настройках панели откройте «Уведомления → Telegram», введите токен бота от [@BotFather](https://t.me/BotFather) и Chat ID. Для ЛС используйте положительный ID и предварительно нажмите «Старт» у бота; для группы — отрицательный ID, включая `-100…`, и добавьте бота с правом отправки сообщений. ID хранится строкой без потери разрядов.

«Отправить тестовое сообщение» проверяет введённые данные без сохранения; пустой токен использует ранее сохранённый. «Сохранить Telegram» подключает новый канал и включает уведомления. Переключатель временно отключает отправку, сохраняя токен и чат. Изменения во время паузы после включения не рассылаются.

Сообщения содержат имя/IP хоста, пул, старый/новый статус и время UTC. Об отключении уведомляем при переходе в «Исключён» или «Отключён вручную», о восстановлении в «Доступен» — только после реального отключения. Переходы «Нет свежих данных → Доступен», «Под подозрением → Доступен» и первоначальное появление доступного хоста без отключения не создают сообщений. Последнее реальное отключение запоминается до полного восстановления и сохраняется при перезапуске. Промежуточные статусы («Под подозрением», «Восстанавливается», «Последний A · защищён», «Ожидает проверки», «Нет свежих данных») не рассылаются; одинаковые результаты не дублируются. После обновления из очереди удаляются старые сообщения о промежуточных статусах и ложном восстановлении после потери свежести; настоящие отключения и восстановления сохраняются вместе с параметрами повторной доставки. Очередь сохраняется в SQLite и повторяет неудачные отправки с учётом лимитов Telegram. При потере ответа после принятия сообщения Telegram повторная доставка может дать дубликат. Ошибки доставки видны в журнале событий. При паузе или смене назначения ожидающие сообщения удаляются; уже отправляемое сообщение может успеть прийти. Токен и Chat ID зашифрованы существующим APP_SECRET. Backend нужен исходящий HTTPS-доступ к `api.telegram.org`; webhook и входящие порты для бота не нужны. API отправки описан в [официальной документации Telegram](https://core.telegram.org/bots/api#sendmessage).

Go checks use Go 1.27.3, module verification/tidy, gofmt, vet, golangci-lint v2.15.0, unit/race tests and production builds. CI uses Ubuntu 26.04; Actions are pinned to reviewed release commits. Dependabot checks Go, Actions and Docker weekly. PR image validation never publishes; publication remains gated on the existing checks.
