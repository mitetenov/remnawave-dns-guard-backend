# Remnawave DNS Guard backend

Панель управления Cloudflare A round robin с проверкой VLESS из России. Отдельный RU-агент проверяет каждый публичный IPv4 через Xray, сохраняя SNI и параметры общего inbound. После серии ошибок панель исключает адрес из DNS, продолжает его проверять и возвращает после восстановления. Недоступный сервер тоже даёт ошибку проверки.

Это самостоятельное Docker-приложение: React/nginx → FastAPI → SQLite; RU-агент запускается на другом сервере. Remnawave используется только для чтения узлов и хостов. В этой версии поддерживаются VLESS TCP/XHTTP и REALITY/TLS, IPv4 и DNS-only A-записи. Не поддерживаются произвольные Xray-конфиги, AAAA и Cloudflare Proxy для адресов пула.


Репозиторий содержит FastAPI/SQLite, API-контракт, тесты и Compose панели.
[Фронтенд](https://github.com/mitetenov/remnawave-dns-guard-frontend) и
[RU-агент](https://github.com/mitetenov/remnawave-dns-guard-agent) находятся в отдельных репозиториях.
Для запуска используются готовые образы Docker Hub; клонировать UI на сервер не требуется.

## Что потребуется

- Linux-сервер панели с Docker Engine и Compose v2, существующий HTTPS reverse proxy и отдельный домен, например `guard.example.com`.
- Сервер в России с Docker и исходящим HTTPS, доступом к публичным IP узлов и панели. Агент не открывает входящие порты.
- Cloudflare-зона, полномочия редактирования её DNS и одинаковый работающий inbound/конфиг на всех узлах одного пула.
- Для импорта: адрес Remnawave и отдельный API token с правами только чтения.

DNS-кеши учитывают TTL, поэтому удаление записи не мгновенно переключает всех клиентов. Последний оставшийся A сохраняется даже при его отказе: это защита от пустого DNS, а не гарантия доступности.

## Запуск панели

В каталоге исходников:

```sh
cp .env.example .env
chmod 600 .env
openssl rand -hex 32
openssl rand -hex 32
openssl rand -hex 24
```

Запишите **разные** результаты первых двух команд в `APP_SECRET` и `AGENT_TOKEN`, третий можно использовать как `ADMIN_PASSWORD`. Заполните `ADMIN_USERNAME`. Не вставляйте эти значения в переписку, git или URL. Значения секретов должны содержать минимум 32 символа; пустые обязательные переменные останавливают Compose. Пример не содержит рабочих учётных данных.

Установите `PUBLIC_ORIGIN=https://guard.example.com`: точный origin браузера без завершающего `/` и без пути. Для HTTPS оставьте `COOKIE_SECURE=true`. Параметры задаются на сервере, фронтенду отдельный API URL не нужен.

```sh
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:8080/api/health
```

Панель привязана к `127.0.0.1:8080`; backend не публикует порт на хосте. HTTPS завершается вашим reverse proxy. SQLite хранится в именованном томе `remnawave-dns-guard_guard-data`, путь внутри backend — `/data/guard.db`. Оставьте ровно один экземпляр backend и одного uvicorn worker: SQLite и DNS reconciliation рассчитаны на такую схему.

Для осознанной локальной разработки можно установить `PUBLIC_ORIGIN=http://localhost:8080` и `COOKIE_SECURE=false`, затем открыть именно этот адрес. Для удалённой панели нужен HTTPS. Не публикуйте HTTP порт в Интернет.

## Reverse proxy

Пример для nginx **на том же хосте**; замените домен и пути сертификата. Для Docker-прокси `127.0.0.1` означает сам контейнер: подключите его к сети панели и направьте трафик на `frontend:80`, либо настройте доступ к хосту отдельно.

```nginx
server {
    listen 80;
    server_name guard.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name guard.example.com;
    ssl_certificate /etc/letsencrypt/live/guard.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/guard.example.com/privkey.pem;
    client_max_body_size 128k;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
```

Сохраняйте `Origin`, Cookie и Authorization. Изменение origin/домена требует обновить `PUBLIC_ORIGIN` и пересоздать backend: `docker compose up -d`. UI использует HttpOnly cookie, SameSite=Strict и проверку origin для изменений. Агент авторизуется отдельным Bearer token. Если добавляете внешнюю авторизацию на proxy, обеспечьте доступ агента к `/api/agent/` без интерактивного браузерного входа; Bearer-проверка приложения должна остаться.

## Интеграции и первый пул

1. Войдите под `ADMIN_USERNAME` / `ADMIN_PASSWORD`, откройте «Настройки».
2. Создайте отдельный [Cloudflare API token](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) с `Zone → DNS → Edit` и `Zone → Zone → Read`. Ограничьте **Zone Resources** только нужной зоной или явным списком зон. Не используйте Global API Key. Введите токен в панели и выполните тест подключения. `DNS Edit` позволяет читать и менять записи, `Zone Read` нужен для выбора зоны.
3. Для импорта создайте Remnawave API token с минимальными scopes `nodes:list` и `hosts:list` (либо read, если установленная версия объединяет права чтения). Используйте API token из панели, не admin login JWT. Не выдавайте write, restart или административные полномочия. Введите HTTPS-адрес панели и токен, проверьте подключение. Проверьте [официальный API установленной версии](https://docs.rw/api/), если названия scopes отличаются. Адаптер сверялся с текущим официальным Remnawave backend 3.4.5 (`GET /api/nodes`, `GET /api/hosts`); подключение к вашей установленной панели требует отдельного теста. Панель DNS Guard не меняет пользователей, узлы, хосты или конфиги Remnawave.
4. Создайте пул: имя, зона, **точный** hostname вроде `vpn.example.com`, TTL (обычно 120), интервал (обычно 60 секунд), пороги ошибок/восстановления (по умолчанию 3/5). Автоматика изначально выключена. TTL применяется к новым и восстановленным записям; существующие/принятые записи сохраняют TTL. Hostname и зону нельзя изменить, пока в пуле есть цели (409); создайте новый пул для другого hostname.
5. Добавьте публичные IPv4 вручную, импортируйте выбранные узлы Remnawave или синхронизируйте существующие A точного hostname. Добавление создаёт либо принимает совпадающую DNS-only запись. Импорт из Remnawave — явное добавление, он тоже меняет DNS. Если узел указан hostname и адрес не определён как публичный IPv4, задайте IP явно. Проверьте импортируемый IP вручную: `node.address` может быть адресом управления, а не клиентским адресом inbound. Proxied A следует предварительно перевести в DNS-only; CNAME не заменяйте автоматически.
6. Сохраните профиль проверки: вставьте VLESS URI работающего клиента либо заполните поддерживаемые поля. UUID, порт, транспорт, SNI, REALITY public key/short ID, flow, fingerprint и XHTTP path/host/mode должны соответствовать inbound **на каждом узле пула**. Используйте VLESS URI отдельного разрешённого тестового пользователя: список Remnawave hosts сам по себе не даёт клиентские credentials для проб. Один профиль применяется ко всем адресам; при разных конфигурациях создайте разные пулы. URI/UUID содержат секреты. Профиль доступен только на запись; API не возвращает сохранённые секреты в UI.
7. Запустите RU-агент по следующему разделу. Убедитесь, что он виден и его контрольная связь здорова. Нажмите проверку и дождитесь реальных результатов: при выключенной автоматике проверки работают, DNS автоматически не меняется.
8. После проверки адресов включите автоматику. Для включения нужны цели и сохранённый профиль. Смотрите статусы, счётчики и журнал (хранится до 30 дней и не более 100 000 событий); пустой журнал после создания — нормальное состояние, демонстрационных результатов нет.

Cloudflare/Remnawave токены можно также задать через необязательные переменные `.env` для первоначальной настройки. Сохранённые интеграции и профиль шифруются в SQLite ключом от `APP_SECRET`; токены не возвращаются API и не должны попадать в логи. Сохраните `APP_SECRET` вместе с резервной копией: простая замена ключа не расшифрует старые значения.

## Агент в России

На RU-хосте клонируйте репозиторий агента; файл `.env` панели ему не нужен:

```sh
git clone https://github.com/mitetenov/remnawave-dns-guard-agent.git
cd remnawave-dns-guard-agent
cp .env.example .env
chmod 600 .env
```

Впишите HTTPS `CONTROL_PLANE_URL` и **тот же** `AGENT_TOKEN`, что у backend. Задайте стабильный уникальный `AGENT_ID`, например `ru-moscow-1`. `CONTROL_URLS` проверяются напрямую, `PROBE_URLS` — через VLESS туннель; можно выбрать подходящие публичные HTTPS адреса с ожидаемым кодом 2xx/3xx. Приватные адреса и переходы к ним не допускаются. `ALLOW_INSECURE_HTTP` оставьте `false`.

```sh
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
docker compose logs --tail=100 agent
```

Xray включён в образ. Агент адресует VLESS outbound непосредственно проверяемому IP, а не round-robin hostname, сохраняя SNI и ключи. Одновременно выполняется не более четырёх задач. Временные конфиги имеют права `0600`, удаляются после задачи; proxy слушает только loopback внутри контейнера. Панель не передаёт произвольные команды или raw Xray конфиги. Источником истины об агенте служит heartbeat в UI; Docker `healthy` проверяет продвижение цикла опроса и успешный авторизованный poll за последние 180 секунд. Прямая контрольная связь может быть недоступна при работающем poll; это отображается отдельно в UI. Healthcheck не проверяет конкретный узел.

## Как принимаются решения

- Ошибка туннеля, сервера или доступности контрольного HTTPS через туннель считается провалом цели **только при здоровой прямой контрольной связи агента**. Сбой самого агента/его канала не превращает весь пул в недоступный. Сообщённый control outage аннулирует текущие задания и сбрасывает серии проверок этого агента.
- Серия из `failure_threshold` принятых неудачных проверок исключает IP. Успех сбрасывает серию ошибок. Проверки исключённого адреса продолжаются; серия `recovery_threshold` успехов возвращает его. Ошибка сбрасывает серию восстановления.
- Защита последнего фактического A действует и для автоматики, и для ручного отключения/удаления. Защищённый отказ виден отдельным статусом. Перед операцией запрашивается текущее DNS, после — проверяется результат. Ошибка Cloudflare не обозначается как успешное изменение.
- Ручное отключение снимает A и выключает мониторинг; адрес **никогда не возвращается автоматически**. Повторное включение — явное действие. Удаление требует подтверждения и удаляет цель, если это безопасно.
- Пауза автоматики оставляет проверки работающими. Она блокирует автоматические изменения DNS; ручные действия остаются доступными. Смена профиля сбрасывает серии и делает старые задания недействительными.
- Задания привязаны к агенту и версии профиля, одноразовые и имеют срок аренды 180 секунд. Для принятия результатов нужен здоровый heartbeat не старше 90 секунд. Повторные, просроченные и чужие результаты не продвигают счётчики. Просроченная задача означает неизвестный результат, не ошибку узла.

Интервал — период планирования, а не строгий SLA. Опрос, очередь задач, таймаут проверки, DNS API и TTL увеличивают фактическое время переключения; 3 ошибки при интервале 60 секунд не обещают ровно 180 секунд. Для больших пулов учитывайте лимит четырёх параллельных проверок и одного RU-агента.

## Эксплуатация

```sh
docker compose logs --tail=100 backend frontend
docker compose restart backend
docker compose pull
docker compose up -d
```

Compose ограничивает CPU, память, число процессов и Docker-логи (3 файла по 10 MiB на контейнер). Сервисы перезапускаются после завершения процесса. Docker не перезапускает контейнер лишь из-за статуса `unhealthy`: проверьте журнал и причину отказа. Backend healthcheck показывает HTTP-ответ сервиса, не соединение с Cloudflare, Remnawave или RU.

Не запускайте второй backend на той же БД. Не выполняйте `docker compose down -v`, если хотите сохранить данные. Для обычного выключения используйте `docker compose down`. `ADMIN_PASSWORD` меняется в `.env` с последующим пересозданием backend; после смены выполняйте новый вход. При ротации `AGENT_TOKEN` обновите backend и RU-агент согласованно. Не меняйте `APP_SECRET` без миграции зашифрованных данных.

## Сборка и CI

Локальная сборка из корня этого репозитория:

```sh
docker build -t remnawave-dns-guard-backend:local .
python3 scripts/smoke_image.py remnawave-dns-guard-backend:local
```

Каждый push и pull request запускает Python-тесты, интеграцию API с агентом,
проверку Compose, сборку и smoke-тест запущенного образа. CI берёт агент из
отдельного публичного репозитория; по умолчанию используется `main`.
Для проверки закреплённой версии задайте repository variable `AGENT_REF` (commit SHA).
После всех проверок `main` публикует AMD64-образ
`mitetenov/remnawave-dns-guard-backend` с тегами `latest` и `sha-<полный commit SHA>`.
Pull request не публикует образы; deploy автоматически не выполняется.

Repository variables: `DOCKERHUB_USERNAME`, `DOCKERHUB_IMAGE`.
Repository secret: `DOCKERHUB_TOKEN` с правами Read & Write.
Compose разрешает закрепить `BACKEND_IMAGE` и `FRONTEND_IMAGE` в `.env`
для обновления или отката. Теги бэкенда и UI относятся к независимым commit SHA.
