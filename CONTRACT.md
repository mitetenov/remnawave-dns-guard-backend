# DNS Guard — agreed implementation contract

User-approved: Cloudflare A-record round robin; Remnawave integration (current API); common config/inbound across nodes in a pool; Docker frontend/backend and separate RU Docker probe agent; failure also counts when server is down; continuously probe auto-excluded IPs and restore after recovery; preserve the final A record; manual add/remove through UI; logs. Sources are published in three separate public GitHub repositories under mitetenov. Live deployment and DNS mutations are outside the repository/CI setup scope.

## Architecture

Go 1.27.2 net/http backend, SQLite persisted in /data (one backend instance; serialized DNS reconciliation), React/TypeScript/Vite frontend served by nginx proxying /api, Go + Xray RU agent polling HTTPS. No Sites/Workers deployment. Backend environment: ADMIN_USERNAME, ADMIN_PASSWORD, APP_SECRET (>=32 chars), AGENT_TOKEN (>=32 chars), DATABASE_PATH=/data/guard.db, COOKIE_SECURE=true, PUBLIC_ORIGIN=https://guard.example.com; optional CLOUDFLARE_API_TOKEN, REMNAWAVE_URL, REMNAWAVE_API_TOKEN. Secrets encrypted in SQLite using key derived from APP_SECRET; never returned or logged. App has no default valid credentials.

All API JSON fields snake_case; IDs strings; UTC times ISO8601; list responses plain arrays unless specified. Errors {detail:string}. /api/health public. Cookie session auth for UI, HttpOnly/SameSite=Strict, secure configurable for localhost; require exact Origin on browser mutations (use configured PUBLIC_ORIGIN, permit requests without Origin only with X-Requested-With: DNSGuard), frontend always sends X-Requested-With: DNSGuard. Agent uses Authorization: Bearer AGENT_TOKEN, never cookie auth. No wildcard CORS.

## Reliability and observation fields

DNS mutations are serialized by a background reconciler, independently of the short SQLite lock. Agent results acknowledge durable acceptance, not completed DNS changes. Manual operations attempt reconciliation synchronously; before any provider write the target and intent are persisted atomically. A 502 after an uncertain provider response leaves the operation pending and retried every 30 seconds, including after restart. Disable and explicit DNS deletion immediately stop target probes while pending; they cannot auto-restore. Deletion without the DNS option removes only local enrollment, cancels pending jobs/intents and never contacts Cloudflare. Legacy pending delete intents without an explicit DNS choice are also completed locally without DNS mutations. Last-record protection returns 409 and restores the previous enabled state. Any proxied A/AAAA at the exact hostname blocks DNS mutations with 409. Pending enrollment can be retried with the same pool/IP without duplicating the target.

Pool additionally returns `dns_checked_at:string|null`, `dns_error:string|null`, `dns_drift_count:number`. The reconciler reads exact-hostname DNS every 300 seconds (failed reads retry after 30 seconds). It reports unmanaged A and managed presence changes without adopting unknown records. Only explicit `/sync` adopts records. An external removal resets streaks: automation can restore a managed enabled target only after new consecutive successes meet the configured recovery threshold. A manually disabled target is never automatically restored, even when an external record reappears.

Target additionally returns `dns_uncertain:boolean`, `dns_pending_action:string|null`, `dns_error:string|null`, `dns_checked_at:string|null`, `dns_drift:boolean`, `probe_fresh:boolean`, and `last_status`. A pending/uncertain DNS state must never be presented as confirmed presence. `status` can be `stale`: the last probe is older than max(180 seconds, 3 × pool interval), or its agent has no healthy heartbeat within 90 seconds. `last_status` retains the last observed state. Staleness is not a failed probe and does not cause DNS removal. Overview additionally returns `stale:number`; its `healthy` count excludes stale or unconfirmed DNS states, and `excluded` counts enabled monitored targets with confirmed absent A records, excluding manually disabled targets.

Session persistence is bound to a keyed revision of the admin username/password. Changing either revokes all old sessions on startup; unchanged credentials preserve sessions across ordinary restarts. The first upgrade from a database without this revision revokes legacy sessions once. The schema migration is additive and automatic; keep a SQLite/APP_SECRET backup before upgrading.

Old profiles omit the field. Lease profiles containing extra only to stable agents >=1.1.0; older workers can still receive other pools without queue starvation.

- PATCH /api/targets/{id} {name?:string,ip?:string} -> Target. Name changes preserve probe evidence and the Remnawave link. Public IPv4 changes preserve target identity and manual enabled state, reset probe evidence/counters, and invalidate old probe jobs. For an enabled target currently in DNS, confirm the new A record before removing the old one, including replacement of the final A record. Excluded and manually disabled targets remain absent. The durable `replace_ip` operation retries after an uncertain provider response and restart; the target retains its old IP until DNS confirmation. Probing and conflicting manual operations are blocked during replacement; the destination IP is reserved against enrollment/sync. Reject duplicate/private IPs and proxied records before storing intent; never delete an unrelated destination record.

## Probe wire protocol (must match exactly)

- POST /api/agent/poll body {agent_id:string,version:string,control_ok:boolean,control_error:string|null} -> {jobs:Job[],poll_after_seconds:10}.
- Job {job_id:string,target_id:string,ip:string,profile:ProbeProfile,timeout_seconds:15}. Job leased >=180 seconds, bound to agent_id and target current profile revision. Issue at most 4 jobs per poll, never overlap same target. Issue jobs for enabled targets regardless of auto-excluded status and even when pool automation paused; interval controls due time. No jobs while control_ok false. Poll records heartbeat and control health; lost agent never equals target failure. Cleanup expired leases -> unknown event, NOT failed target.
- POST /api/agent/results body {agent_id:string,results:[{job_id:string,ok:boolean,latency_ms:number|null,error:string|null}]} -> {accepted:number}. Single-use jobs, reject/ignore duplicate, unknown, expired, wrong agent, stale profile jobs; out-of-order does not advance counters. Result requires fresh healthy control heartbeat. Sanitize error (agent emits enumerated reasons only). Persist successful/failed consecutive streaks, reset opposite. Failed streak >= threshold queues serialized removal of the exact CF A record unless last actual A; status protected when prevented. Recovered streak >= threshold restores auto-excluded target ONLY if manual_enabled=true and pool automation enabled. Every DNS operation refreshes actual records first and verifies afterward; errors do not falsely mark successful mutation. Pending DNS operations retry idempotently every 30 seconds; automatic retries require a fresh healthy agent, current profile revision and still-valid streaks. The accepted count confirms durable result/intent storage, not completion of Cloudflare work. Pool pause prevents DNS mutations, not probes.

Agent env: CONTROL_PLANE_URL required HTTPS (ALLOW_INSECURE_HTTP=true only dev); AGENT_TOKEN; AGENT_ID=ru-1; XRAY_BIN=/usr/local/bin/xray; CONTROL_URLS comma-separated default https://ya.ru,https://www.cloudflare.com/cdn-cgi/trace; PROBE_URLS default https://www.gstatic.com/generate_204,https://cp.cloudflare.com/generate_204. Control healthy if at least one direct HTTPS URL gives 2xx/3xx (no redirect to private IP); results only submitted while control is healthy, recheck before submission. Per job build narrowly scoped Xray config with loopback HTTP inbound on ephemeral port and ONE VLESS outbound addressed to job.ip (do not resolve pool hostname), preserve SNI/key. Use Xray + HTTP(S) request via local proxy, any configured target success. Disallow arbitrary raw Xray config/command from backend. Validate public IPv4, ports, UUID/profile fields. Runtime temp configs chmod 0600, cleanup subprocess/config after each job. No credentials or raw errors in stdout. Limit concurrent jobs=4 and retries/time budget < lease; controls outside tunnel. Tokens not forwarded on redirects; HTTP verify enabled.

## Telegram delivery

Host status changes (including computed stale, manual disable, DNS exclusion and recovery) are atomically captured in a SQLite outbox. Repeated checks with unchanged effective status do not enqueue messages. A dedicated worker sends snapshots containing host name/IP, pool/hostname, old/new statuses and UTC timestamp, independently of probes/DNS and outside the database lock. It sends at most one queued message per second, preserves ordering across retries/restarts, backs off on errors and respects Telegram retry_after. Errors exposed in API/events never include provider bodies or token-bearing URLs. Pausing or changing credentials/destination discards pending messages and baselines current statuses; resuming does not replay changes from the pause. An already in-flight message may still arrive. Delivery is at least once: if Telegram accepts a message but its response is lost, a retry may duplicate it.
